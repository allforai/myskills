# role-profiles / vpc-per-role（S12b · user-role-definition）

## R1 车主（消费侧）
- JTBD：当车辆刚发生小额剐蹭、须向保险公司求偿时，尽快拿到该得的赔付，而不靠电话来回补影像把周期拖到按月计（本产品不存在时这件事仍要办成）。不是「把照片上传到某端」。
- VPC：Jobs=求偿并知道案子是否在办；Pains=电话+来回传图、快也一个月才结；Gains=少被追材料、钱尽快到账。Relievers=一次交出现场影像、进度可查而不必电话催。Creators=小额件结案周期可预期缩短。
- 多客户端：`clients[]` 仅上游已给的拍照上传+小程序查进度；`feature_parity=full`（单端），不扩 iOS/Android/Web。合法 `client_type` 表无小程序，不把小程序改写成 `react-spa`/`swiftui-ios`。

## R2 理赔员（生产/运营侧；人≠客户端）
- JTBD：当材料真伪/新旧难辨的小额剐蹭堆在手上时，对「是否本次损伤、责任几成、该赔多少」做出自己签得出去的裁定。
- VPC：Jobs=辨伤与责任并给出可交代赔额；Pains=争议件必须人眼看细节、系统风险分不能当拍板、吞吐压人；Gains=少错赔、同类件更快结。Relievers=照片/维修单/当日天气/历史报案可同案放大比对。Creators=分数只参考、裁定落到操作者。
- Producer-side closure：消费裁定与到账的是车主（保险公司是买方、消费的是结案结果）；生产裁定（责任比例、处理意见、赔额）的是理赔员；运营判读作业的也是理赔员。理赔员消费的影像由车主生产；维修单生产者（维修厂）上游无使用面，不声明其客户端。保险公司无具名「必须人看」步骤，不发明管理后台。
- 面的模式（先于 `clients[]`）：上游无 agent/自动化/接口，不采用 agent 面，也不假装已有内部工具。采用人机屏，依据是例外条款而非量——①旧伤/新伤的人眼视觉判断（放大比对+天气/历史）；②责任比例与赔付金额的不可逆决定且由操作者承担责任。明确排除：「一天几百份」、CRUD、字段多（那是 agent 的活）；效率卖点不单独构成屏幕。
- `clients[]`：[{app:"adjuster-workbench", client_type:"next-js", platform:"desktop-web"}]；`feature_parity=full`。桌面工作台由全天看图比对支撑；`next-js`/`react-spa` 留给 tech-architecture。
