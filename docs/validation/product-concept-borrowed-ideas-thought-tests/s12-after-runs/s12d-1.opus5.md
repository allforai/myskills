# S12d · user-role-definition（家教撮合）— `role-profiles.json` / `vpc-per-role.json` 内容

## 角色与 job（JTBD；不含产品/功能/界面，各带"当…"，产品不存在时仍然想要）
- **R1 家长**：当我要把孩子每周的课交给一个陌生大学生时，让站在门口的人始终是我当初见过并同意的那个人，且我付出去的钱只对已经上完的课负责。（今天靠亲戚推荐＋试课看人满足）
- **R2 大学生家教**：当我有固定空档、想靠自己的专业换钱时，让附近愿意出这个价的家长看见我，并且课上完后钱按时到手。
- **R3 平台运营**：当一笔交易的双方对结果不服时，替平台给出一个自己要担责的裁断，并让当事人知道依据是什么。

## VPC（Jobs / Pains / Gains → Pain relievers / Gain creators）
- **R1**：Pains＝"试课那次来的人跟后来上课的不是一个"、"一次交一学期的钱，我心里没底"、抽成不透明；Gains＝换人有交代、钱与课时对得上 → 授课人身份的一致性可被核验；已上课时与已付金额始终可对账、可中止。
- **R2**：Pains＝没渠道被家长看见、月结拖账；Gains＝单源稳定、到账准时 → 打卡即产生计费事实；有可被家长看见的位置。
- **R3**：Pains＝每天 400 单新增、100+ 投诉退款工单，裁断所依赖的事实散落各处；Gains＝每个裁断都留下依据 → 打卡记录、订单条款、投诉陈述在同一件待裁事项里聚齐。

## Producer-side closure check
- 生产＝R2 授课（打卡产生计费事实）；消费＝R1；运营＝R3。**R3 先不算客户**，按事务逐项定模式。
- 量不构成开界面的理由：400 单/天、100+ 工单/天、"字段多""就是 CRUD"都不是依据——那是 agent 干的活。
- **agent interface（工具/API 契约，不出 `clients[]` 条目）**：家长订单字段校验（科目/年级/地址/课时单价皆为可判规则）、按打卡课时结算课时费、连续差评触发提醒、工单事实聚合与分派。
- **human-facing screen（两项，各有指名的必须由人看的一步）**：① 学生证与身份照片跟本人是否一致＝视觉判断；② 退款与暂停接单＝动别人收入的不可逆决定，运营要为它签字担责。
- **缺依据的一项**：按城市调整服务费比例——上游没说谁签字、多久调一次，既可能是一次性配置也可能是要人担责的定价决定 → 不预设界面，留作开放问题。
- **未知须如实记录**：上游明确没给平台方人数与现状。故 ①② 只声明"存在一步必须人看"，其载体（自建后台 / 接进团队已有工具）等用户确认，不因此扩成控制台。

## 多客户端声明
- **R1 家长**：`clients[]` = parent-ios、parent-android；`feature_parity: full`（两端做的是同一件事）。`client_type` 是架构级选择、不静默决定：推荐默认 `flutter-mobile` 一套两端，备选双原生（`swiftui-ios` + `kotlin-android`）；web 无证据，不声明。
- **R2 家教**：`clients[]` = tutor-ios、tutor-android；`feature_parity: full`。打卡发生在上课地点，移动端为必需；`client_type` 同 R1 待确认。
- **R3 运营**：不声明 app 型 `clients[]` 条目；agent interface 那批是工具契约，①② 的承载方式待用户定。**不写 `cli`**——cli 是人在终端，是界面的替身而非 agent 面。

## 留给编排器 / 后续节点
- 开放问题（本节点不替用户定）：平台方人数与当前处理方式；服务费比例调整的责任人与频率；①② 的承载方式（自建后台 or 团队已有工具）。
- 证据缺口：家长侧有 6 位原话，**家教侧零条行为事实**，R2 的 job/pains 是从"按课时、月结"反推的 → Mom Test 口径未满足，建议回补后重跑 R2 段。
- 未立为角色：孩子（真正上课的人）——上游只有家长在决策与付钱，没有孩子的行为事实；是否独立成角色（谁反馈教学效果）留作问题，不擅自新建。
