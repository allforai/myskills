# 角色定义（user-role-definition）

## JTBD
- R1 家长（消费）：当孩子某科需要一对一补课、要有人按约定出现时，找到能稳定来的大学生，且不必先把整期学费交给中间人。
- R2 大学生家教（生产）：当自己有可排课时、想靠补课挣钱时，被正在找家教的家长看见，并按实际已上课时拿到钱。
- R3 平台运营（运营，尚非客户）：审核证件与订单、处理投诉/退款、按打卡结算、差评停号、按城调服务费。编制与现行做法上游未给。

## VPC
- R1 Pains：试课的人≠后来上课的人；一次交一学期心里没底；中介抽成高、信息不透明。Gains：同一人持续来；按次付、看得到人。Relievers：人证可对上、不整期预付给中间人。Creators：能核到来的就是这个人。
- R2 Pains：没法被家长看见；中介抽走大部分。Gains：按课时收、上完打卡、月结。Relievers：不经高抽成中介也被找课家长看见。Creators：上完的课能对上再收到钱。
- R3 不以「上后台」为 job；Pains/Gains 因编制/工具未知不编造。

## Producer-side closure
消费 R1，生产 R2（课），运营 R3。有人消费≠运营已是客户端。量/CRUD/字段多不是开屏理由。
- 学生证与身份：看证件真伪，属视觉判断，人看的屏仅为这一步的例外候选。
- 家长订单（科目/年级/地址/单价）约 400 单/日：结构化字段，走 agent 接口，不开屏。
- 打卡结算：计算与付款指令 → agent 或团队已有工具。
- 退款；连续差评是否暂停接单；按城调服务费：不可逆资金/账号/定价，须有人对结果负责。
- 投诉（迟到/放鸽子/换人）：要判事实，依据不足，不据此开屏。
编制、现有工具、能否走 agent 均未记录 → 不为 R3 声明 clients[]，不设控制台。

## 多客户端
- R1/R2：须有人对着的端，但上游未记录平台。情境含地址/到场/课后打卡，人在场侧需要随身端；不可从证据选定 client_type。clients[] 与 feature_parity 不冻结。
- R3：不声明 clients[]。若落成 agent 接口则是工具契约不是 app；cli 算人盯的屏替身，不是 agent。
