# user-role-definition
## 角色 / JTBD / VPC
**R1 家长**（消费履约）Job：当孩子某科需要人上门补课，雇到试课与后期同一人，且不必把整期学费先交给中介。
Pains：试课换人；整期预付没底；中介抽成/不透明。Gains：人固定、按课时付、知道来者。Relievers：人证一体可核；课时后付。Creators：投诉能处理、钱能退。
**R2 大学生家教**（生产授课；消费曝光与结算）Job：当想靠会的科目课余挣钱，被有该科目/年级需求的家长看见，上完一节拿到那一节的钱。
Pains：家长看不见；中介抽整期；被临时换人。Gains：被找到；按课时、打卡、月结。Relievers：需求能碰到人；打卡后结算。Creators：在校身份被信。
**R3 平台运营**（生产信任事务）Job：当每日约400单新需求、投诉+退款100+件时，把该信的人审过、该付的课结清、把放鸽子/连续差评者停掉，双方仍能成交。
Pains：假证、迟到/放鸽子/换人、退款扯皮、差评号仍接单、城市费率不一、队列积压。Gains：单与工单能闭合；结算对上打卡。Relievers：证/单审核、投诉退款、打卡结算、停号、按城调费。Creators：争议有裁决。
## Producer-side closure
消费：R1要固定的人+非整期预付+投诉有着落；R2要被看见+按课时到手。生产：R2产授课与学生证/身份材料；R1产需求（科目、年级、地址、课时单价）。
运营：R3产审核证件与订单、处理投诉（迟到/放鸽子/换人）、按打卡结算、退款、差评提醒与是否暂停接单、按城调服务费。无R3则消费承诺无人兑现。上游未给运营人数与现行处理方式，不编造编制。
## 多客户端声明
无已记录的平台决策，不选定 `client_type`（选项必须来自能力表）。
R1 `clients[]`：未定。约束：上门/课后，需要随身客户端。
R2 `clients[]`：未定。约束：同上，外加课后打卡与月结查看。与R1是否同一app、`feature_parity` 未定。
R3 `clients[]`：未定。约束：日量审核/工单/结算需要坐席队列客户端；与C端功能不同，`feature_parity` 工作假设 `independent`，待确认。
不把「上传学生证」「发布订单」写成 job（那是产品强加的用法，不是没本产品时仍要完成的事）。
