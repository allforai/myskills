# S12b — `user-role-definition` 产出（车险剐蹭判读台）｜无人值守
## 角色与 JTBD（job 不含产品/界面，带"当…"，产品不存在时依然想要）
- **R1 理赔员（主使用者）** — 当手上压着几百份剐蹭材料、其中一批照片说不清是旧伤还是这次造成的时，给出一个自己敢签、日后被质疑也站得住的责任比例与赔付金额，并且当天把队列清完。
- **R2 车主（材料提供方 / 进度查询者）** — 当车被剐蹭又得照常开车时，把该赔的钱拿到手，并且随时知道还差什么、什么时候到账，不用被反复要材料。
- 记录："就想拍两张照片，钱快点到"是 R2 给出的**候选方案**（`candidate_solution`），不是 job；挂在上面那条情境下，是否只拍两张由用户确认，本节点不把它改写成需求。

## Producer-side closure check（谁生产 / 谁运营）
- **事故照片**：生产者 = R2（上游明确）。消费者 = R1。闭环成立。
- **维修单/报价**：R1 要"比对维修单"，但上游没说谁产——修理厂？R2 拍照上传？R1 手录？**cause unknown**，答案来自用户/保险公司现行流程。此项定死之前，R1 的维修单对照能力没有输入源，下游不得当作已闭环。
- **风险分**：上游只说"系统给出"。**生产者与阈值运营者未定**（模型方？保险公司风控？）。本节点不凭空设"算法运营"角色，也不声明任何自动判读——上游没有 agent/自动化/接口材料。
- **争议升级的接收方**：R1 的"敢签"和"往上递"隐含一个理赔主管/质检角色（抽检、复核、争议拍板）。记为 **R3 候选角色（未确认）**，不发 clients，不进 `roles[]` 正式项。
- **SaaS 侧运营**：客户是保险公司，开通账号、配置规则、导入历史报案得有人做（实施/客户成功）。同样**未确认**，记为候选。
## 多客户端声明（`clients[]` / `feature_parity`）
- **R1**：`clients=[{app:"claims-desk", client_type:"next-js", platform:"desktop-web"}]`，单客户端（等价 legacy `app`+`client_type`），`feature_parity` 不适用。依据：上游"主要使用时长在判读台"+放大比对细节需大屏；无移动端证据，故不虚构 iOS/Android 端。
- **R2**：单客户端（拍照上传 + 查进度，微信小程序）。但能力文件的 `client_type` 表里**没有小程序/H5 这一项** → 不硬套 `react-spa`/`next-js`，置 `client_type:"pending"`、`status:"blocked_on_schema"`；候选：新增 `wechat-miniprogram`，或按 H5 并入 `react-spa` 并记偏差。此项未定前 R2 的 `clients[]` 不算完成。
- 若保险公司之后要求小程序 + H5 并存，则 `feature_parity:"partial"`、`parity_exceptions:["拍照依赖相机权限，H5 降级为相册上传"]`——这是条件写法，不作为已定结论。
