# product-review — 发现能力测试（真实代码库）

日期：2026-09-17。结论：**前两轮思维测试只测了分类与取舍（观察是喂给受试者的）；这轮让受试者自己在一个埋了缺陷的代码库上找问题。六次采样零误报；召回从基线的 2.5–3.5/5 提到修复后的 3.5–4/5，两处规则改动各堵住一种漏法。**

受试者按用户要求用 Sonnet（resolved `claude-sonnet-5`，六次一致），主会话 Fable。每轮两次独立采样。

## Fixture

[`fixtures/product-review/ledgerly/`](../../fixtures/product-review/ledgerly/)：一个 Flask 发票工具，`build.sh` 重建出带三条提交的仓库。范围内两份工作（三元组已确认，直接交给受试者）：JOB1 发出发票并知道已送达（cross-exam 判 J1 done）；JOB2 标记已收款并在仪表盘看到本月收入（无 J 覆盖）。

埋 5 条应发现（D1 发送无过程反馈、D2 首屏无引导且 6/9 菜单是桩、D3 收入只算 `sent` 于是标记已收款反而少钱、D4 天气组件装饰且提交信息可查、D5 校验错误走 flash 而 SMTP 缺失走裸 JSON），5 个陷阱（惯例功能、旧依赖、把 Clients 页当装饰、配色口味、对 JOB1 重走或写 missing_job）。答案表见 `answer-key.md`，不进 packet。

无浏览器、无 WebSearch、不运行产品：全部 `code-only`。

六次都另外发现一条未埋但成立的问题：发票邮件正文只有一行数字，`pdf.py` 建好了却没接进 send 流程。D4 的 adopt/defer 协议都允许（分歧在"工作集是否覆盖产品主要用途"），不计对错。

## 两处规则改动

**D01 → D02：Facts 完成标准加五镜头行。** 基线两次都漏 D1，而"核心动作有没有过程反馈"就写在镜头表里；`J done` 让受试者把整份 JOB1 当作已判定，第 4 问没在它上面认真过。改法：每份工作在引导 / 过程反馈 / 下一步 / 状态一致 / 回来理由五格各写一句观察，`J done` 只免第 1、2 问。效果：D1 从 0/2 观察到变 2/2。

**D02 → D03：格子改 `有 | 缺 | 未查`，写 `缺` 必须对应 `R` 或写不立项原因。** D02 里"未见"歧义暴露：两份报告写"引导 未见"后就放过了——"没有引导"本身就是缺陷，受试者把"交代过了"当成"处理过了"，D2 从两次半中退成两次漏；D02b 还出现观察到 D1 却不立项。效果：D03 里 D2 恢复（中 + 半），每个 `缺` 都指回 R 号或给出理由，D1 两次都进了树（一次独立、一次并入并说明）。

两处都是验收标准，不教方法：说的是报告里必须有什么、缺项时必须交代什么，不说怎么看代码。

## 能力边界

稳定发现的（D3、D4、桩页、邮件太薄）都是能从代码里直接读出来的；分歧和漏掉的（D1、D5）都要在脑子里走一遍"用户点完看到什么"。镜头行让这类观察被逼出来，但 D03a 仍把"状态一致"写成 `有`（只查了 flash 样式，没看 500 handler）——纯读代码时状态一致性的召回还不稳。

## 尚未验证
