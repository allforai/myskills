# S12b 角色与价值（user-role-definition，无人值守）
## 角色与 job（JTBD，去产品化）
- **R1 理赔员**｜job：当一份说不清是旧伤还是本次新伤的材料摊在手上时，当天给出一个我敢署名、日后被翻出来也站得住的定责与金额结论。
- **R2 车主**｜job：当车被剐了一道、还得照常开着上班时，尽快把修车的钱落到自己账上，中途不被反复叫回来补材料。
- 车主原话"就想拍两张照片，钱快点到"里，"拍两张照片"是**用户的候选方案**，挂在上述情境下并列记录，不改名成 job 或机会。
## VPC
- **R1**｜Pains：一天几百份看不完；争议件靠电话来回；风险分不可解释却要自己担后果。Gains：单件判读耗时可控、结论可追溯。Pain Relievers：新旧伤放大比对与当天天气/历史报案随案同屏、判读过程留痕。Gain Creators：争议件与顺畅件分流，顺畅件压到最短。
- **R2**｜Pains：一个月才结案、不知道卡在哪、被反复要材料。Gains：一次交齐、进度可见。Pain Relievers：上传即提示材料够不够、关键节点状态可查。Gain Creators：无争议件快速结案。
## Producer-side closure check（谁消费／谁生产／谁运营）
- 消费方：车主（消费赔付结论与进度）、保险公司（消费赔付成本结果——买单方，但上游没给它任何使用场景，故不立角色、不给端）。
- 生产方：事故照片由 R2 生产（有端）；**维修单的生产者上游未点名**（修理厂／车主代传／定损员？）→ 不臆造角色，记 open question。
- 运营方：风险分的产出、调优与误判复盘归谁，上游未提；上游又明说"没有 agent／自动化／接口能力"→ 既无依据声明 agent 接口，也无依据声明人用界面，**该角色不声明 clients[]**，模式作为开放问题留给用户。
- **R1 是运营侧角色，但界面例外成立**，依据是上游点名的"必须有人看的步骤"：人眼看细节、放大比对旧伤/新伤（视觉判断）＋"最后拍板必须是人"、结论由其署名担责（不可逆决定）。依据**不是**"一天几百份"、不是 CRUD、不是字段多。
- 争议升级后的复核／仲裁人：上游未提 → 不声明，记 open question。

## 留给编排器／后续节点
- 三条 open question（维修单生产者／风险分运营者／争议复核人）回交互式确认，本节点不代选；确认前 roles[] 不为它们出现 clients[]。
- `client_type` 枚举缺"微信小程序"：回 capability/bootstrap 层裁决（扩枚举，或改判为 H5 走 `react-spa`）；在此之前 R2 的 client_type 保持 unknown，属阻塞项而非笔误。
- ui-design／product-verify：R2 只按 supported_features 两项设计与验收，不得以 parity 为由补齐判读功能；R1 的界面正当性来自上面那个具名步骤，验收要盯放大比对与署名担责链路。
- tech-architecture 触发点（本节点不决定）：大图放大比对＋历史报案调取 → 媒体存储/CDN、检索与延迟预算；风险分的可解释性影响 R1 担责，属技术风险候选。
