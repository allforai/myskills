# S12a 产出 — 节点 `user-role-definition`（邻里童装交换）

## 角色与 job（JTBD；不含产品/界面/功能名，带"当…"情境）
- **R1 换出方**：当家里衣服玩具已经小了、玩腻了，扔掉心疼又不愿一个个去问朋友时，把它们交到用得上的人手里，不必拍照标价、不必寄件。
- **R2 换入方**：当孩子又长一码、不愿为只穿三个月的东西花钱时，拿到确认干净完好的下一码，且不用开口跟人讲价。
- **R3 小区运营人（那 2 位兼职者）**：当每天有十几二十条杂事、而自己只有下班后那点时间且不拿工资时，把它们处理完并且不让它侵占家庭时间。
- R1 与 R2 **大概率是同一批家长在不同时刻**（5 位访谈者两头的话都说了）：按两个 job 记，不按两个人群记；"换出意愿远大于换入意愿"是未验证假设 → O2。

## VPC（右栏为候选方向，不是已确认功能；功能定义归下游）
- **R1** Pains：逐个私聊问人、拍照标价耗时、回收商不到十块｜Gains：东西有去处、不欠人情｜候选：不必逐个询问就被需要的人看见；无议价的交付方式。
- **R2** Pains：不知道谁家有什么、不愿讲价、怕拿到破的脏的｜Gains：省下一码的钱、同小区当面取｜候选：先知晓谁家有什么；成色由换出方以外的人担保（担保人未定 → O1）。
- **R3** Pains：事务碎且随时来、核实住户无权威名单、裁决要背锅｜Gains：下班后半小时清干净、有据可依｜候选：待办集中一处、裁决有可引用的规则（形态未定 → D1）。

## Producer-side closure check（谁生产、谁运营）
- **消费方 R2 的供给全部由 R1 生产**，平台不自产任何库存 → 冷启动时 R1 侧为空，闭环不成立；这是概念层风险，不是运营问题 → O2。
- **运营必须由真人 R3 承担**：上游 5 类事务（违规下架、放鸽子投诉、住户核实、月度积分、纠纷裁决）没有一类能在无人时自行完成，因此 R3 是正式角色，不是"我们自己顺手做"。R3 的 job 只在本产品存在时成立，这是运营角色的固有性质，不适用"拿掉产品仍成立"检验——但不声明它，闭环就是假的。
- **住户核实这条缺生产方**：每天十来个新用户要确认是否本小区住户，上游没给名单来源（物业名册？门禁？邻居背书？）。**原因未知，答案在用户那里**，不在仓库也不在搜索；来源定下来之前这条 job 不可实现。
- 上游事实中不存在第三方审核方、担保方、结算方，本节点不虚构。
