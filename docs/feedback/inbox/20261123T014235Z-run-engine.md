## Anonymous Meta-Skill Feedback

Category: run-engine
Meta-skill version: unknown

### Failure Pattern

Declared repair loop unreachable: program-repair is hard_blocked_by all seven QA nodes, including program-e2e/visual/experience nodes that are themselves hard_blocked_by the failed QA nodes. When an upstream QA node (server-rule-parity, server-runtime-qa, payment-verify, program-build-verify) fails, the downstream QA nodes never run, so the repair node never becomes ready. The engine opens the route, never dispatches, and ends with exhausted_repair_loop with ledger spent=0, a misleading label. Readiness validation accepted the shape. Suggested fix: the repair node should depend only on its QA nodes that can run (or loop satisfaction should treat never-ran downstream QA nodes as satisfied), and the engine should report 'unreachable_repair_node' instead of exhausted. Also seen: integration nodes that must edit shared entry files (main.ts, modules.go) stale upstream producers whose acceptance pins file hashes; and a repo-wide no-time.Now check in an upstream acceptance failed on a later QA node's non-_test.go harness files, deadlocking the graph.

### Expected Behavior

The meta-skill should record or repair this class of workflow issue without exposing project-specific information.

### Suggested Fix

Update the relevant skill, bootstrap rule, validator, or orchestrator helper so future projects do not hit the same failure pattern.
