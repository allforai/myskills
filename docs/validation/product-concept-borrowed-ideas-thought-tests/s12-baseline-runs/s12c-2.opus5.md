# S12c — user-role-definition 产出（`role-profiles.json` + `vpc-per-role.json` 摘要）
## 角色 / JTBD / VPC（job 判据：不含产品·功能·界面，带"当…时"，本产品不存在时仍然想要）
**R1 买家（设计外包 / 自媒体内容生产者）— 消费方**
- J1「当我把带图、带乐的稿子交给客户之后，不会有人找上来说这素材我不能用」（访谈原话："最怕用完了被人找来说侵权"）
- J2「当交期临近、我心里已经有画面时，很快拿到对得上那个画面的素材，不用翻半天」；J3「当客户或发布平台追问来源时，当场把'这次使用被允许'讲清楚」
- Pains：侵权追责成本不可预期；筛选耗时；免费站条款读不懂且会变；AI 生图被部分客户拒收、风格不稳｜Gains：一次付费覆盖大多数稿件；来源可出示；风格可预期
- Pain relievers / Gain creators（方案侧草案，定稿归 concept-crystallization）：可存档的按用途授权凭证；取用不必逐张决策；来源与授权范围随交付件一起走。注：上游"想按月订阅一个库"是**用户候选方案**、不是 job，故未写入 J1–J3；是否只做订阅归 business-model。
**R2 创作者（摄影师 / 插画师 / 音乐人）— 生产方**
- J1「当我手上有已完成、只卖过一两次的作品时，让它继续产生收入而不必自己逐单谈授权」；J2「当我要定下个月拍什么画什么时，知道自己哪类作品真被人用了」
- Pains：逐单谈授权耗时；不愿买断而失去作品；分成口径与到账不透明｜Gains：持续被动收入；保留著作权（平台只代授权）；下载与用途数据
- Pain relievers / Gain creators（草案）：一次上传多次授权；可核对的月结；审核不通过时给出可据以修正的理由
**R3 平台运营 / 审核 — 运营方（closure 要求其存在；内部切分未定，见 Q1）**
- J1「当有人申请入驻或上传新素材时，在不把上架拖慢的前提下把不能上的挡在库外」；J2「当版权方或被侵权者找上门时，尽快查清库里同类素材并给出可交代的处置」
- J3「当一个月结束时，把该付每位创作者的钱算准、打出去，且事后能对账」（退款同月内可追溯）
- Pains（**证据等级：inferred**——上游只给了事务清单，没给人数与现状，无运营侧访谈，按 Mom Test 这不是行为事实）：审核量与人手不匹配；判断主观难复核；错杀伤创作者、漏放伤买家；结算出错只能人工追｜Gains：处置有依据且留痕；重复投诉可批量处理；月结可自证
## producer-side closure check（每项事务落到人，不留悬空）
- 消费 R1 → 生产 R2 → 运营 R3。上游 6 项事务归属：入驻审核=R3；素材审核（版权/肖像/敏感）=R3；侵权投诉与下架=R3；按下载量分成打款=R3；订阅退款=R3；应版权方要求批量排查=R3（**触发方是外部的版权方，见 Q3**）。
- 闭合结论：R2 的收入依赖 R3 的月结，R1 的"来源清楚"依赖 R3 的审核与下架链条；没有 R3，这两侧的 job 都不成立 → R3 是必需角色，不是可选的"管理后台"。
- 未闭合项：R3 的人数、现在怎么处理这些事务，上游都没有；本节点不替用户决定它的切分与工具形态（Q1/Q2），也不据此推断权限模型。
