# S12「运营默认给 agent 接口，不默认给人点的管理后台」——基线与对照

日期：2026-09-21。对应路线图第二节的单主题候选（原表里没有这条，来自用户 2026-09-21 的观察：
"现在的产品根本不怎么需要后台，给 ai agent 留接口就可以了"——澄清后专指**给人点的 admin/Vue 管理后台**，
不是服务端）。

## 要防的失败（改前改后都按这条判）

**红（失败）**：运营角色被声明了一个给人点的 web/SPA 管理端（`react-spa` / `next-js` / Vue 之类），
并当作要实现的产品面交付；整个过程没有出现"这件事能不能不给屏幕、只给 agent/接口"的判断，
也没有把它标成待用户确认的疑问。

**绿（通过）**：声明了运营角色，但不把"给人点的 web 后台"当默认交付——要么显式提出这个选择
（含 agent 接口 / 脚本 / 现成工具等更便宜的替代）并标为需用户确认，要么不声明该客户端而把问题留给用户。

## 判据（运行前写下）

- **S12a（低量级运营）**：运营是 2 个兼职的人、一天十几二十条、顺带做。预期绿。
  红 = 长出一个要规划实现的 web 管理端。
- **S12b（回归对照，防过度矫正）**：这个产品的主用户**就是**操作者，判读照片、比对单据、拍板赔付
  本来就是主工作台，且主要使用时长在这里。预期**保留面向人的工作台是合理的**。
  红 = 因为"运营"二字把明显需要人眼判断的主工作台也降级成只给 agent 接口。

S12b 是防止改动改过头的那一半：这条规则不能变成"凡是运营就不给界面"。

## 第一轮的发现：s12a 的场景泄露了答案（方法问题，不是结论）

`s12a-1` 是绿的，但**这个绿不能算数**：它在产出里直接引用了场景里的线索——
"2 人兼职养不起两套原生"、"十几二十条/天 × 2 人兼职，新增一套管理端是纯负担"。
也就是说，"不要给人做管理端"这个判断是**我把答案写进上游**喂出来的，不是能力文件带出来的。

这和上一轮记下的 S4 教训同型（上游材料过于具体弱化了证明力），当时是 S9 补上的。
所以本轮补 **s12c**：运营事务真实、量级不小，但上游**不说平台方有多少人、不说他们现在怎么处理**，
把"要不要给人做界面"这个判断真正交回给能力文件。

s12a 保留作为"暖场景"与 s12c 对照，不删。

## 第二轮的发现：s12c 也没打中（第二个方法问题）

s12c 两遍跑出分歧（s12c-1 声明了 `react-spa` ops console，s12c-2 把 R3 的 `clients[]` 留空并显式抛问），
说明这个场景确实能拉动行为差异。**但它的运营事务里混了"审核素材（版权/肖像/敏感）"这种要靠人眼看图的工作**，
而"视觉判断"本来就在"仍该给人做界面"的清单上。也就是说 s12c-1 声明 console 可能是对的，不是失败。

第三个问题：**冻结的判据写成了三重合取**（声明了管理端 且 无判断 且 未标记待确认），
结果 s12c-1 虽然声明了 `react-spa`，但因为另抛了 O1，按字面反而算绿。这是判据写得差，不是受试做得好。

所以补 **s12d**：把运营事务全部换成**纯记录与数字**的活（审证件、审订单、投诉、按月结算、退款、调费率），
没有一点需要看图的成分；同时保留"不告诉平台方人数与现状"与"量级真实"（每天 400 单 / 100+ 工单）。
判据也重写为单向：

- **红** = 运营角色的 `clients[]` 里出现给人点的 web/SPA 管理端（`react-spa` / `next-js` / Vue）
  并当成要实现/要设计的产品面，**并且**全篇没有出现过"能不能不给屏幕、改成给 agent/工具/接口"这一层判断。
- **绿** = 要么不声明该客户端（留空或挂问），要么显式把这个选择作为待确认项抛出（含 agent 接口 / 脚本 /
  现成工具等替代）。

## 三轮下来已经能看到的一件事

到 s12c 为止 4 个有效受试（s12a-1、s12b-1、s12c-1、s12c-2）里，**没有任何一个把"给 agent/接口"作为运营侧的可选项提出来**。
s12c-2 最接近（抛了"现成工单/表格"），s12a-1 抛了 `cli + 直连数据`。也就是说：
能力文件既不禁止人用界面、也不提示接口这条路——运营面到底长什么样，全靠受试自己发挥，两遍就能跑出相反结果。

## 基线结论（s12d 打中）

s12d（纯记录与数字的运营活、量级真实、不说平台方人数与现状）两遍都声明了给人点的管理端，
且两遍都没有触及"能不能不给屏幕"这一层：

- **s12d-2 强红**：`ops-console`(`next-js`) 不只被声明，还被写成了下游契约——
  "`ui-design` 与 `product-verify` **必须**为 R3、R4 出界面并按角色验收"。运营面在没有被问过一次的情况下，
  变成了必交的 UI 与逐角色 UI 验收。
- **s12d-1 弱红**：声明 `ops-console`(`react-spa`)；closure 段里写了"不默认 aut审核就够或一个后台就够"，
  但那句话说的是**规模**，不是**形态**；产出里没出现接口这条路。
- **s12b（对照）仍绿**：主用户就是操作者的判读台保留 `next-js`，候选运营角色不发 clients。改动不能动它。
- **s12a / s12c 不计入结论**：s12a 场景泄露了答案，s12c 混进了靠人眼看的审核工作，两者证明力不足（保留作对照）。

因此基线**未通过**，需要拟改动。改动方向见下面「拟改动」。

## 结论：采纳

- s12d：改前红（opus-5 2/2 红，grok 1/1 同型），改后 **4/4 绿**，且两模型都逐条执行了新规则（引用了"量不是理由"、
  "那是 agent 干的活"、"cli 是界面的替身")，不是换个说法敷衍。
- s12b：改前绿、改后仍绿，且改后把保留工作台的依据从"主要使用时长在此"升级成了**具名例外**。回归未被误杀。
- 因此改动**通过**，保留在 worktree 并提交。

## 已知局限

- 每个格子仍然只有 1–2 份样本，不是稳定性采样；发现过"同一场景同模型跑出相反结果"（s12c、s12d-before-3 与 1/2 之间）。
- s12a 与 s12c 两场景证明力不足（前者泄露答案、后者混进视觉工作），结论不靠它们，但也没有删。
- 场景是手写的，不是真实 run 的输入；"纯记录与数字的运营活"这个切面只有 s12d 一个场景。
- `s12d-before`-3（grok）没有声明具体 `client_type`，所以"改前红"里有三条是**公开声明了管理端**、
  一条只是**按量推出需要坐席客户端**。这条差别不改变结论（改动防的是那个推理），但写清楚免得读表的人误以为都是同一种红。
