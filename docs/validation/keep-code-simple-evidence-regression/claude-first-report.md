- **类型**：**实现等价**；依据：**已查证**（语义推导，未实测）

### (a) 源码可证明的行为（不依赖任何外部假设）

1. **invoice 级唯一性在应用层未实现**。`collect.py:3` 与 `:6` 均以 `request_key` 为键，全文**没有任何对 `invoice_id` 的唯一性检查**。同一 invoice 配两个不同 request_key 会走到两次 `:5` 的 charge。`README.md:7` 第一句"one invoice may be collected once"在本函数内没有对应实现。**这是本次最重要的一条**——它不依赖外部条件即可证明；外部条件只决定这个缺口是否已被别处补上。
2. **无异常处理与补偿逻辑**。全文无 `try`/`except`/`finally`、无冲正/退款路径。`:5` 之后抛出的任何异常都直接冒泡，**已发生的 charge 不会被撤销**。
3. **非原子的 check-then-act（TOCTOU）窗口**，跨越整个 `gateway.charge` 调用：`:3` 检查 → `:5` 外部副作用 → `:6` 写入。
4. **"已扣未记"窗口成立**：`:5` 抛异常时（超时/连接重置属经典二义性），钱是否已扣无法本地判定，而账本此时无任何记录；`:5` 返回后、`:6` 完成前的进程崩溃同理。
5. **失败终态不可区分**：函数不向调用方区分"未扣款"与"已扣款但未记账"——无异常包装、无状态标记。
6. **重试参数不校验**：同 key、不同 `invoice_id`/`amount` 调用时，`:3-4` 会**静默返回旧记录**，不报错不告警。
7. **返回账本记录的引用**：`:4` 与 `:11` 返回 `ledger[request_key]` 本身，未拷贝。调用方对返回值的原地修改会直接篡改账本。
8. **顺序方向正确的一侧**：`:5` 先于 `:6`，因此在"charge 失败即抛异常"的前提下，"记而未扣"不会发生；`:6-10` 是先构造完整字面量再整体赋值，账本内不会出现字段级半条记录（前提：`ledger` 为普通 dict）。
9. **billing 零测试覆盖**：`test_contracts.py:5-7` 只导入 catalog 与 search，`:14-19` 两个用例只覆盖 CSV 与 query，全仓库无 billing 测试。

### (b) 未知的外部条件（本仓库内不可判定，`README.md:3` 明确无真实 gateway）

1. gateway 是否真正兑现 `idempotency_key`；失败时抛异常还是返回失败哨兵值。**若返回哨兵值而不抛异常，`:6` 会把一次失败扣款记成 receipt**，(a)8 的结论随之失效。
2. `ledger` 的真实身份：进程内临时 dict、跨请求共享单例，还是持久化后端。
3. 并发模型：仓库内无线程/异步/锁痕迹，也无调用方。
4. 是否存在外部对账/补偿作业能发现"已扣未记"的孤儿交易。
5. 调用方是否保证"一 invoice 一 request_key"（决定 (a)1 是否已被外部消解）。

### (c) 可能后果（条件性，非既成事故）

- 若 (b)1 为"gateway 不幂等"或存在超时二义性，且调用方按常规重试 → **重复扣款**，账本只留一条记录，对账无法察觉差额。
- 若 (b)3 存在并发 → 两个线程同时越过 `:3`、同时执行 `:5`，账本后写覆盖先写 → receipt 丢失或双重扣款。**CPython GIL 不提供保护**：单次 `in` 与单次 `[]=` 各自原子，但"查—扣—写"跨越多条字节码和一次外部 I/O。
- 若 (b)2 为非持久/非共享 ledger → 进程重启后同 key 重试会重新打 gateway，README 的第二条契约在应用层完全失守。
- 若 (a)1 成立且 (b)5 不成立 → 同一发票被合法地收款两次，直接违反 `README.md:7` 第一句。
- (a)7 → 调用方无意的原地修改会静默污染对账数据，且无任何测试会发现。
