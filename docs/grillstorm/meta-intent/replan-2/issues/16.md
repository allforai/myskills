## What to build

以连续事件场景验证产品决定在中断、反悔、资料冲突和再次逆推时的权威与历史保持，确保恢复不是重新猜测用户意图。

这是保留的补充思维测试批次 2/4；目标是实际执行并验证 Skill 决策，而不是只写测试计划。场景判据属于评估侧，不得整份票据连同预期结论直接交给受测 agent。

## Acceptance criteria

- [ ] 提出产品问题后用户未回答便离开，再进入 bootstrap：验证待决仍待决，不把中断或沉默记为批准。
- [ ] 用户已确认部分决定、其余未决：验证恢复时仅询问未决或新受影响事项，不重复完整访谈。
- [ ] 确认后用户反悔并调整意图：验证旧决定保留历史，新决定明确取代旧意图，后续规划使用当前有效决定。
- [ ] 旧产品基准与用户最新决定矛盾：验证矛盾被展示，旧文件存在不能自动覆盖新决定；缺少确认依据的旧基准不能冒充批准。
- [ ] 用户删除某个意图后，代码仍有该功能，再次逆推：验证不会把删除意图悄悄复活为需求，并保持删除原因和历史。
- [ ] 删除／调整意图发生在讨论阶段：验证目标产品代码未被立即删除或改写；仅依赖未决问题的工作受阻，无关已确认工作保留。
- [ ] 无人值守入口遇到未决决定：验证不现场发起产品访谈，不捏造批准；用户回到交互入口解决后可继续。

### 执行、证据与关闭条件

- [ ] 以独立、干净上下文执行每个场景；受测 agent 仅接收场景、原始仓库／历史资料、当前 Skill 和该步用户输入，不接收判据、预期结论、怀疑或其他测试报告。预定中断续接场景仅传其应有的持久化状态。
- [ ] Claude、Codex 分别实际执行；记录平台、被测版本、独立会话身份、场景输入、逐轮问答、工具行为、生成产物及状态变化。没有相关能力或未执行的平台标为无法验证，不以另一端结果代替。
- [ ] 评估侧单独持有逐场景判据，并用实际问答、产物、差异和执行状态判断通过／失败／环境无法验证；不能用提示词含关键字、文件存在或 agent 自报代替行为验证。
- [ ] 使用隔离测试项目和合成数据，不影响真实产品、不开展生产调用、不安装无关依赖或重写产品需求；优先复用已有 fixture 与校验边界，不新建独立测试框架。
- [ ] 失败场景记录最小可复现步骤、输入／版本、观察与预期差异，并创建或关联责任缺陷及对应实现票。已有关联缺陷则复用，避免重复。
- [ ] 缺陷修复后使用新上下文复测受影响场景并记录前后证据；只修改一句提示词或创建缺陷票不能关闭本测试票。所有必测场景在两端验证通过才完成，未解决失败或环境无法验证须保持未完成并明确原因。
