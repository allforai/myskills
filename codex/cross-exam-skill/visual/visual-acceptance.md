# Visual acceptance — 可选视觉验收 facet

本文件所在目录记为 VISUAL_ROOT。仅用户选择视觉 facet 后加载。协议通用；SwiftUI 再读 swiftui/baseline-guide.md、review-criteria.md、brand-spec-template.md 和 platforms/swiftui.md；Web 再读 platforms/web.md（七个维度对浏览器的取值与施加方式）；Android 再读 platforms/android.md。其他平台先按本文通用步骤做，维度取值在 environment 类逐项与用户确认。不需要安装外部 Skill。

## 运行合同

沿用 cross-exam 交互、独立取证、本地/开发靶、只记录不修复的约束。唯一审计输出根是 docs/cross-exam/<run>/；不修改产品源码。发现 UI 时自动列为候选 facet，先由用户选中。已知没有取证/看图能力时声明限制，视觉问题无法自证，其他 facet 可继续。

1. 独立 census 从代码枚举页面/弹层/入口/状态，运行探索补齐动态入口。记录无法枚举的类别；未完成普查不能声称全 App 覆盖。**同一次普查还要从代码读出布局宽度阈值**（`layout_thresholds`：布局在哪些逻辑宽度上会变，每条带 `path:line` 出处）和**支持的宽度范围**（`width_range`：最小与最大宽度，出处是窗口最小尺寸、支持的设备家族或最大显示器）——各平台在哪找见 platforms/*.md。分辨率自适应不是一个"面"，它是每个面在每个宽度上的另一副样子；阈值不入账，device 轴就只剩用户随手说的那一个尺寸。
2. 独立 prober 打开代表性页面并截图；主会话结合源码、设计文档与实图生成 visual/observed-style.md。截图中的缺陷不是基准。真实敏感数据改用已有合成数据；无法避免时停该项，要求用户处理。
3. 逐类展示候选规则、冲突和参考图，让用户确认 direction/color/typography/layout/spacing/icons/components/navigation/feedback/states/motion/environment。每次确认记录用户原意与时间。颜色等规则不能靠安装自带偏好自动获准。**environment 类里逐轴问一次"要不要支持"**：普查官从代码读出每个轴的支持值（语言：打包语言含默认与 RTL；appearance：浅色 / 深色 / 应用内主题；dynamic_type：缩放或字号档位；orientation：声明支持的方向），逐轴摆给用户，问本次验收覆盖哪些——不问就默认全覆盖，不许替用户放弃。用户放弃的值逐条记 `declined`（值 + 用户原话 + 时间；语言在 `locales.declined`，其它轴在 `axis_support.<axis>.declined`），不从 `supported` 里删——"代码支持但产品不打算发"本身是要留在报告里的事实。用户没放弃的值全部进该轴，矩阵拒绝漏掉的。**layout 类里从代码读出的定值不是规则，是候选，每条候选要先分类：钉死（pinned）还是流式（fluid）**。钉死是指规则把某个元素钉在一个宽度上（固定宽度、max-width、居中列、"列宽等于设计稿"），流式是指元素随窗口宽度变化（主列拉伸、侧栏贴边、分隔线随列走），流式规则的文本里不出现宽度字面量——gutter、分隔线粗细这类尺寸有字面量就不是 layout 类的流式规则，去掉数字或按 spacing 的写法记；每条规则写成对象声明自己是哪一种：`{rule, pinned: false}` 或 `{rule, pinned: true, ends}`，字符串不可审，校验器拒渲。钉死的定值只有在 device 轴两端（`width_range` 的最小与最大）各成立一次才能冻结为规则——`ends` 写明它在两端各自允许的空区（与内容宽度之比或绝对值；形状见数据接口「钉死的 layout 规则」），没写两端的规则不可审，校验器拒渲；否则宽窗上照抄代码的 820px 居中列与它右边一整块空背景都"符合规则"，reviewer 无句可引。分类是主会话摆给用户的判断，校验器只核对声明与文本不打架：声明流式却写着宽度字面量的规则拒渲。同一页面里同类元素的对齐基准不一致（一列居中、一列贴边、第三个另一个宽度）是候选冲突，必须摆给用户；用户接受也按原话记进 confirmation。
4. 冻结 visual/visual-baseline.json 与 interaction-baseline.json，每个文件含 categories 映射；每类含 rules（非空规则列表）或 reason（该类不适用的原因，此时 rules 可为空列表），二者必有其一；另含 reference_images、confirmation、confirmed_at。保留用户批准图片的范围和例外。SHA-256 按文件原始字节计算，两个摘要独立存储。
5. 生成 visual/surface-inventory.json 与 case-matrix.json，并把同一矩阵写入 ledger.visual_cases。每个页面按适用 state/device/os/appearance/dynamic_type/locale/orientation 完整笛卡尔积；键盘、权限等归入 state。具体环境值在 environment 类确认，不能用“所有”代替枚举。**device 轴的下限由阈值定，不由用户的屏幕定**：每个阈值两侧各至少一个有效宽度（portrait 取短边、landscape 取长边），且要触到 `width_range` 的两端；用户的实际屏幕只是其中一个值。**每个轴的下限由代码支持的值定，不由用户的习惯定**：`locales.supported` 和 `axis_support.<axis>.supported` 减各自 `declined` 的每个值都要在每个页面的对应轴出现（轴值可以是"浏览器 zh-CN + 站点 en"、"系统 dark + 应用内 light"这样的组合，支持值须是独立的段或 token；一个组合值是一条用例、读回只证明一个值，所以每个支持值要有自己的用例——"系统 dark + 应用内 light"一条不能同时算作 light 和 dark 的覆盖，矩阵按一对一匹配拒绝）；只在部分值可达的页面用自己的 `locales.only` / `axis_scope.<axis>.only` 加 basis 收窄。声明了支持值的轴，capture 必须带应用内读回值 `readback.<axis>`，且读回值要是该用例轴值里的一段——组合值"系统 dark + 应用内 light"读回 light 就只证明了 light；RTL 语言另须 `readback.direction: rtl`。设了不等于生效，缺读回或读回不符一律拒渲。`matrix.py` 拒绝展开不满足的清单，校验器回放冻结清单时同样拒绝。无数量上限，分批但不抽样。不适用项须有 reason 与 basis（出处），构造不了不等于不适用。

**展开之后再检查一遍：要不要抽象。** 全矩阵先展开，`matrix.py` 在 stderr 打印总数与逐轴分布；看着这个数，逐页面判断哪些轴对它是**相互独立**的——语言只换字串、深浅色只换颜色 token、字号只按 rem 缩放，这些轴之间不需要两两交叉；依据要来自代码（样式是否按 token 走、有无按语言或主题分支的布局代码），写进 `abstractions[].basis`。摆给用户确认后写 `confirmation` 与时间；用户不确认就不抽象。被声明独立的轴只在**锚点**（`anchor`，缺省是各轴第一个值）上各自变化，缺省仍与 state 轴交叉（`cross_with`，默认 `["state"]`：深色不是只拍一张，而是每个状态各一张；写 `[]` 才是只在锚点拍一次，写 `["state","device"]` 则再与设备交叉），其余轴的全积仍保留；会改布局的值用 `keep_coupled` 留在全积里（RTL 语言必须留）。被抽象掉的组合**不删**：矩阵里照样有它们的行，带 `abstracted_by`，报告计为 abstracted，不算未测也不算通过。**抽象可被推翻**：某个独立轴的用例落了 gap 或 drift，这个轴的独立性就存疑，报告点名并把它抽象掉的用例列为"需重展开"，续跑时重新展开这些行。逐轴覆盖表（每个轴值：已裁决 / 应测）让"抽象后还测了什么"一眼可见。
6. 逐批派 fresh-context prober。传具体用例、设备和状态、基线摘要，不传 Golden、预期结论或怀疑。视觉定位可读入口代码，但不与禁止读源码找路的 journey 探针混用。一个模拟器/设备一次只由一个 prober 操作，独立设备才可并发。分批以比较组为界：同一比较组、同一环境（除 state 外六维相同）的用例必须在同一条 entry 里裁决，校验器拒绝被拆开的组；单页各自通过不等于全局一致。每例实图；motion 用例至少两张带时间顺序的原始关键帧，另存录屏用于节奏判断。不能用 Preview、模拟图、Token 或截图元数据代替实际 App。
7. 对每批原图运行独立 visual-reviewer（读 prompts/visual-reviewer.md）。传冻结基线、用例和图片，不传作者观点、其他审查报告。主会话自身不能替代 reviewer。
8. 当前平台 fresh-context reviewer 必需。另一平台 CLI 经只读版本/帮助检查和实际看图调用可用时双审。当前平台的 reviewer 不传 `model`，继承会话模型；另一平台的 CLI 用它当时可用的最强模型（定靶时用 `--help` / 模型列表探测，不在技能里写死）。reviewer 的 finding 直接决定阻断，永远不降档（见 SKILL.md "模型"），entry 的 `agent_model` 记当前平台 reviewer 实际生效的字面量。不用 resume/fork 既有会话；CLI 参数按当前 --help，只读工具/沙箱，不开启 bypass。外部 reviewer 通过标准输出返回 JSON，由主会话原样保存；不得把 JSONL 事件流当报告。单独 evidence 子目录，每个 reviewer 报告完成前不暴露另一份。
9. 第二端失败重试一次；仍失败写 degradation_ref（两次尝试与原因），该批 dual_degraded，保留独立单审结果。当前端无独立审图能力仍无法自证。reviewer 声称“打开了图片”只是记录，主会话还须核查实际图像读取工具记录，不把字段当证明。
10. 双审 high/medium 取并集。reconciliation 记录全部 session_id:finding_id 和 disagreements；有阻断发现不得判 done。阻断按 finding 指向的用例计：一条 entry 只被指向其 visual_case_ids 原图的 high/medium 阻断，同批其余用例可拆成独立 entry 共用同一份报告各自裁决；finding 引用的图片必须在该 reviewer 的 inspected_images 内。gap 是缺失/冲突/破损，drift 是偏离批准方向，unprovable 是缺环境/基线/有效证据。没有确认基线只记录差异与 unprovable。未跑项 not_examined；用户停止后渲染全部剩余项。

基线未确认时先建立已知页面用例，写失败原因文件并给对应项 unprovable，不伪造已确认字段。中断后按原基线摘要与构建续跑；构建或基线变化建立新的审计 run，避免旧缺口/截图混入新结果。不得自动重写 Golden。

## 数据接口（路径约定）

surface-inventory.json 顶层含 platform（web | ios | android | macos，必填，其它字符串拒展开——Electron / Tauri 写 web；web 时每个页面必须声明 scrollable，每条 capture 必含 capture_mode / headless / scrollbars / scroll_profile / capture_tool，校验器拒缺项）、form_factor（desktop | mobile | both：目标是桌面窗口、手机还是两者都有；web 必填，macos 隐含 desktop，ios / android 隐含 mobile；隐含值可以升成 both——iPad Stage Manager、Android 桌面模式、macOS 兼有 iPad 布局都是——写成相反的单值拒展开；desktop 或 both 时必须声明全局 `width_range`，且其 max 不得低于桌面下限 1920——matrix.py 里的常量 `DESKTOP_WIDTH_FLOOR`——展开与校验器回放都拒绝；用户拉不动的窗口（Electron `resizable: false`、固定尺寸工具窗、kiosk）在 `width_range` 上写 `fixed_window: true` 且 min 等于 max，basis 写出不可缩放的代码出处，这种窗口没有宽端可测，豁免下限；页面自己收窄的 `width_range` 不受此限，但收窄只给在被去掉的宽度上确实不可达的页面，basis 写明为何不可达，且不可达要有普查官从代码读到的依据：普查官原件里有 `width_range` 时，收窄的页面必须对上普查官 `ui_surfaces[]` 里一条自带 `width_range` 的面（innerWidth 路由守卫、仅桌面路由、尺寸类门槛）——三种对法：同 id、同 entry，或页面自己写 `census_id` 指名普查官条目的 id——收窄不得比它更窄，对不上的按页面名拒渲并列出这三种对法；一句 basis 不是依据；收窄的范围必须落在全局范围之内，且至少一个页面的范围要触到全局 max，否则展开拒绝——所有页面都收窄就是把宽档从矩阵里藏掉。device 轴的有效宽度必须落在适用范围之内：用户的 2560 显示器要进矩阵，就把 max 提到 2560，钉死的规则也就要在 2560 写空区，而不是让一张范围之外的截图无句可引。form_factor 与 width_range 都在 environment 类摆给用户确认；普查官原件（`form_factor`、`width_range`、`layout_thresholds`、`ui_surfaces`）由校验器从 `visual_acceptance.census_ref` 按摘要绑定的文件读出（见下文「普查官原件」），逐项比对，inventory 只许比普查官从代码读出的更宽，不许更窄：form_factor 只许加不许减：普查官读出 mobile 或 desktop 的可以升成 both（用户可能知道代码没写的显示器），读出 both 的写成任一单值、读出 mobile 的写成 desktop、读出 desktop 的写成 mobile 都是丢掉一端，拒渲并点名两个值；`width_range.max` 低于普查官的、`min` 高于普查官的、普查官读到了范围而 inventory 没声明，都拒渲并点名两边的数；普查官读出的每个阈值宽度都要出现在 inventory 的 `layout_thresholds` 里，少一个按宽度点名拒渲，多加不限——只比单位是平台逻辑单位（web px、ios / macos pt、android dp）或没写单位的条目，普查官以 rem / em 读出的阈值 inventory 已换算成逻辑单位而校验器不知道根字号，跳过不比也不拒，单位不在 px / pt / dp / rem / em 之内按形状无效拒渲；原件里没有某个键时该项不比，原件形状不对给出原因而不是异常）、abstractions（[{axis, basis, confirmation, confirmed_at, keep_coupled, cross_with}]，可全局或按页面）、anchor（{axis: 值}，可全局或按页面）、layout_thresholds（[{width, basis}]，逻辑单位：CSS px / pt / dp）、width_range（{min, max, basis}）、locales（{supported, default, rtl, basis, declined: [{locale, confirmation, confirmed_at}]}，`supported` 原样来自普查官——普查官的 `locales` 与 `translation_keys` 原件在绑定的普查官文件里，校验器比对两处 `supported`，inventory 少了任何一种拒渲；放弃只能走 declined。缺失的翻译 key 不进视觉矩阵，按 SKILL.md "孤例还是一类"建 pattern）、axis_support（{<axis>: {supported, basis, declined: [{value, confirmation, confirmed_at}]}}，appearance / dynamic_type / orientation 等其它轴的同一套声明，原样来自普查官加用户确认，校验器同样拿绑定的普查官原件比对，少了任何一个支持值拒渲；locale 轴只能在 `locales` 声明一次）、可选 devices（设备名 → {width, height, scale, basis, 可选 fixed_width}，让 device 轴可以写模拟器/机型名而不只写 `WxH@scale`；fixed_width 为 true 的条目——Slide Over、分屏、自由窗口——旋转不改宽度）；单个页面可用自己的 width_range（带 basis）收窄适用阈值，如只在桌面可达的管理页。surfaces 每行含 id、entry、kind、axes（上述七维到字符串数组）、motion_states、scrollable（Web 必填：目标视口下 scroll_height > client_height；为 true 时 state 轴必须含至少一个 `scroll-` 开头的滚动位置状态，矩阵展开拒绝缺它的页面），以及可选 groups（比较组名列表，如 buttons、navigation、forms；共用同一组件或模式的页面标同一组名）。
运行 `python3 VISUAL_ROOT/matrix.py <inventory>` 输出完整矩阵（含 abstracted_by 标记），原样保存 case-matrix.json 并写入 ledger.visual_cases；stderr 的总数与逐轴分布是抽象审查的依据，先看它再决定要不要抽象。
**钉死（pinned）的 layout 规则。** 基线 layout 类的 rules 条目都是对象，两种形状：流式（fluid）规则写 `{rule, pinned: false}`，钉死规则写 `{rule, pinned: true, ends}`；字符串条目、缺 `pinned`、`pinned` 不是布尔值，校验器都拒渲并点名两种形状。`pinned` 是决定，宽度字面量只是对声明的核对：声明流式的规则文本含宽度字面量（数字后接 px / pt / dp / rem / em / 像素 / pixels，或 `width` / `max-width` / `min-width` 后接数字）或带 `ends` 的，按"声明为流式却写了宽度"拒渲；声明钉死却没写 `ends` 的拒渲。`ends` 是 {宽度: {empty}} 映射，键恰好是适用 `width_range` 的 min 与 max 的十进制字符串（各一条，不多不少；固定尺寸窗口 min 等于 max 时只有一条），每条的 `empty` 含可见字符（零宽字符、BOM、盲文空格不算），写该宽度下允许的空区：一个 reviewer 拿尺子能核对的量——相对主列或内容宽的比例（"两侧各 ≤ 主列宽 50%"）或带单位的绝对值（"≤ 240px"），可附用户原话说明为什么；`empty` 里必须有一个可量的界——数字后接单位（px / pt / dp / rem / em / % / 像素），"用户说没事"、"无限制"、"." 这类没有量的句子校验器拒渲，理由说明空区要有可量的界，"多宽都行"也写成数字（"≤ 100% 内容宽"、"≤ 2000px"）。规则可带 `surface` 指向 inventory 里的一个页面：该页面自己声明了收窄的 `width_range` 时，两端按它的 min 与 max 算（只在桌面可达的管理页不必写手机宽度那一端），没声明就回落到全局范围；指向 inventory 里没有的页面拒渲，无论钉没钉宽度。钉死的规则缺任一端、键不是冻结范围的两端、`empty` 为空、钉死却没有可用的 `width_range`，校验器都拒渲并点名规则；rules 不是列表、条目不是带 `rule` 的对象、`ends` 不是映射，给出原因而不是异常，所以早于这条规则冻结的旧 run（layout 规则还是字符串）渲染为拒绝而不是崩溃。这条检查只看 visual-baseline.json：interaction-baseline.json 的 layout 类写的是手势距离、抽屉行程，不是窗口宽度，条目形状不受此限。图标尺寸、圆角、字号这类不是布局宽度的定值不属于 layout 类，写进 layout 类就得声明钉死还是流式，声明流式又带字面量会被拒。钉死宽度的句子只能在 layout 类：写进 spacing / components 等其它类的宽度字面量校验器点名拒渲，要求移回 layout 并写两端。中文数字或没有单位的宽度（"约八百二十像素"、"宽 820"、"列宽等于设计稿"）字面量识别不到，但它照样钉死了一个宽度：写成 `pinned: false` 是对基线撒谎，不是躲过了检查——校验器核对的是声明，reviewer 引用的也是声明。
增加页面/状态必须重新展开、保留原未测清单，不手工删减组合。
用例 ID 根据页面和环境组合内容生成，重排页面不改变身份。冻结 inventory、matrix 原始字节摘要；校验器重新展开清单核对完整矩阵，renderer 即使遇到 ledger 漏页也展示冻结矩阵中的未测项。

**普查官原件。** census_ref 指向普查官返回原样保存的文件（约定 visual/census.json），census_digest 是它原始字节的 SHA-256。校验器从这个文件读 `form_factor` / `width_range` / `layout_thresholds` / `ui_surfaces` / `locales` / `axis_support` 做上面全部比对：摘要不符拒渲（"普查官原件摘要不匹配"）；ledger 顶层若仍带同名键（含 `translation_keys`），只能是逐字副本，与文件不一致按键名拒渲——删掉或改掉顶层键不再关掉任何一项检查，普查官原件与基线、inventory、矩阵一样是冻结输入。没有 census_ref 的旧 run 回落到 ledger 顶层键比对（缺键即不比），报告视觉节注明普查官原件未绑定；UI 目标（inventory 有 surfaces 且声明了 width_range / locales / axis_support 之一）既没有 census_ref 也没有任何顶层原件键的拒渲："普查官原件缺失（census_ref）"。运行审查模式在运行开始按当时可用能力冻结，同一 run 内升降都不允许：dual 不能在 entry 静默改成 single，single 也不能中途升 dual；能力变化（另一平台 CLI 装好或失效）建立新的审计 run。
基线每类 reference_images 是 {相对 run 的原图路径: SHA-256} 映射；两份基线合计至少一张可解码、经用户确认的参考图。确实不适用的类别可为空映射，须记录原因。不能只有文字或代码规则。

visual_cases 每行：{id, surface, state, device, os, appearance, dynamic_type, locale, orientation, motion: false}；不适用增加 applicability: not_applicable、reason、basis；ledger 行相对冻结矩阵只允许多这三个键，身份字段必须逐字相同。未测状态由 renderer 从采信裁决计算，不信任自报通过。

manifest = {captures: [{case_id, state, device, os, appearance, dynamic_type, locale, orientation, build, captured_at, baseline_digest, interaction_digest, inventory_digest, matrix_digest, images: [原图路径], image_digests: {原图路径: SHA-256}}]}。每条 capture 另记 `readback`：`{<axis>: 应用内读回的值, direction: ltr | rtl, width: 应用内读回的布局宽度}`，inventory 声明了任何 `width_range` 时 `width` 必填且须等于该用例设备值在该方向下的有效宽度（Web 读 `window.innerWidth`，SwiftUI 读窗口/场景宽度，Android 读 `windowSizeClass` 对应的 dp 宽），device 值只是对窗口的声称，开小窗拍"2000 宽"那档靠这一项拒掉；声明了支持值的每个轴都必须有读回值且与用例轴值相符，RTL 语言用例缺 `direction: rtl` 拒渲（各平台怎么读见 platforms/*.md）。Web capture 另必含 capture_mode（viewport | full_page）、headless、scrollbars（native | hidden | overlay）、scroll_profile（platforms/web.md 定义的页面读回值）、capture_tool；state 以 `scroll-` 开头的用例只接受 capture_mode viewport 且 scrollbars native 的 capture，否则拒渲——无头全页截图里没有滚动条也没有折叠线，滚动类断言不能从它推断。每条 capture 的 build 与四个摘要必须等于冻结运行配置。构建含 commit 与 dirty 状态及可识别当前产物的构建标识；截图必须能追到该构建。PNG/JPEG 原图保留，附图的缩放裁剪不覆盖原文件。motion 另含与 images 一一对应的 frame_times_ms（非负、有限、严格递增），至少两张不同像素内容的帧；复制文件、更换编码或重复路径不算新帧；还必含 recording（相对 run/evidence 的录屏路径，非空文件，不能是某张帧）与 recording_digest（SHA-256），缺一拒渲。关键帧检查不证明节奏正确，录屏才是节奏证据。

review report = {platform: claude|codex, session_id, independent: true, build, baseline_digest, interaction_digest, inventory_digest, matrix_digest, inspected_images: [原图路径], image_digests: {原图路径: SHA-256}, reference_images: {基线参考图路径: SHA-256}, status: passed|findings, findings: [{id, severity: high|medium|low, rule, observation, images: [原图路径]}], inspected_recordings: [实际打开过的录屏路径], recording_unreadable: 原因}。本批含 motion 用例时，该批全部录屏必须出现在 inspected_recordings，或写 recording_unreadable 说明该 reviewer 为何读不了视频（此时它只审了帧序列）。所有 reviewer 都没审阅录屏时，含 motion 用例的 entry 不能判 done：有帧序列上的发现可判 gap，否则把 motion 用例拆成单独 entry 记 unprovable（visual_failure_ref 写明无视频读取能力），静态用例照常裁决。reviewer 独立读取并计算摘要，五项绑定必须匹配冻结运行，且覆盖该批全部原图及全部基线参考图。图片键逐字沿用 manifest 的 images 字符串（相对 run/evidence）和基线的 reference_images 键（相对 run），校验器精确比对，主会话不得改写报告。

## 镜像与消费者

本包只有 `shared/visual-acceptance` 一份源码，`sync.py` 把它整包镜像为四处 `visual/`：cross-exam 两个平台（`claude/superstorm/knowledge/cross-exam/visual`、`codex/cross-exam-skill/visual`）和 meta-skill 两个平台（`claude/meta-skill/scripts/visual`、`codex/meta-skill/scripts/visual`，后者经符号链接指向前者），每处都与证据引擎镜像 `engine/` 并排，`matrix.py` 从自己包旁边找引擎。镜像的是整包而不是只抄 `expand_inventory` 与读回检查：已安装的插件只带自己的根目录，抄出去的函数会在引擎修一次后漂走；`test_mirrors.py` 与 `evidence-engine/test_single_definition.py` 只认镜像。

meta-skill `/run` 的 visual-verify 门（`scripts/check_visual_evidence.py`）从本包读矩阵规则（`matrix.expand_inventory`：device 轴跨每个阈值、触到 `width_range` 两端、桌面下限、`resize-` / `scroll-` 状态、支持值一一入轴）、capture 检查（`validation.web_capture_reason` / `scroll_reason` / `rtl_reason` / `width_readback_reason`，与引擎的 `readback_reason` / `images_reason`）和钉死规则检查（`validation.pinned_layout_reason`），验收标准写在 `claude/meta-skill/knowledge/capabilities/visual-verify.md`。它不读 ledger、不做 `render_report.py` 的裁决，reviewer 拓扑按 meta-skill 自己的 ADR-0002/0003；本文的运行合同（独立取证、只记录不修复、完成度只由 `render_report.py` 产出）不因镜像多了一处而改变。两边对"什么样的 capture 算证据"只能有一个答案，答案在这里。
