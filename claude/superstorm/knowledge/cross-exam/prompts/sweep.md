# 扫全实测官（sweep）— 固定 question 模板

扫全模式把同一句 question 盖到每一个操作面上，这句话就是覆盖模板：漏一个观察口，所有面一起漏。
所以它不即兴写。派发 = prober.md 全文 + 本文件全文 + 输入 JSON；纪律与返回合同都沿用 prober.md。

## 输入合同（在 prober.md 的合同上只改 question 与 states_to_capture）

`question` 一字不改地用下面这句，只替换尖括号：

> 触发 <surface id>「<surface name>」（入口 <entry>）后实际发生了什么：触发前、触发中、触发后界面各是什么样；
> 触发期间出现了哪些请求或外部调用（方法、目标、请求体摘要、状态码、响应体摘要；零条就记零条，并记下
> 你用什么手段抓的、同一会话里它抓到过哪条别的请求）；
> 触发后该操作对应的服务端资源和本地存储各读回来是什么（只涉及一边的，另一边写"不适用"并说明为什么）。

`states_to_capture` 固定五项：

```json
["00-触发前初始态", "01-触发中（加载/等待/禁用态，一闪而过也截）", "02-触发后界面态（提示、跳转、无变化，如实记）",
 "03-请求记录（抓取手段 + 同会话已抓到的任一其它请求 + 请求去向 host/进程/拦截层 + 触发前后请求列表原文，文本文件）",
 "04-后置数据（服务端资源与本地存储各自读回原文，不涉及的写不适用，文本文件）"]
```

cli / api 目标没有"界面"：00/01/02 换成命令前状态、命令输出、命令后状态，03/04 不变。

## 三个观察口，一个都不能省

界面反馈、请求记录、数据读回并列。请求记录里"零条"只有在同一份文件能证明抓取手段活着（同会话抓到过
别的请求）时才是观察；抓取手段没抓到任何东西，写 `could_not`，不写零条——"没发请求"和"没抓到"是两件事。
数据读回两边各读一次：只读本地会让"写了本地、该上传却没上传"的操作看起来三面一致。

盘问官事后对着三面裁"契约是否兑现"：三面一致才是 done；界面报成功而请求为零或数据未变，是假成功；请求已落而界面无反馈，是反向的接线缺口。
你只带回三面，不判哪一种。

## 与 prober.md 不同的两点

- 五个状态对应五个证据文件，缺一个就是"返回残缺"，会被同一输入重派。
- 前置条件（登录态、需要先有的数据）由你自己造；造不出走 `could_not`，不绕。
