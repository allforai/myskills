### S1 — 把 `src/catalog/export.py` 的手写 CSV 逻辑换成共享的 `write_csv`

- **类型**：覆盖取舍（绝大多数输入实现等价，存在一处已定位的输出差异）；**依据**：条件性（差异点未实测）
- **现状与证据**：
  - `src/catalog/export.py:1-11` 手写了一整套 CSV 引号规则：命中 `, " \r \n` 时加引号、`"` 翻倍、`None`→空、其余 `str()`、每行 `\r\n`。
  - `src/catalog/history.py:4-5` 只是 `return write_csv(rows)`；`src/shared/tabular.py:5-9` 用 `csv.writer` 的 excel 方言，规则与上述逐条对应（QUOTE_MINIMAL 的触发字符集恰为分隔符、引号符与行终止符中的 `\r`/`\n`）。
  - `README.md:5` 明确写着"Existing exports use the shared `write_csv` interface" —— **`export_catalog` 是唯一没有遵守这条明确承诺的实现**。
  - 全库搜索（`export_catalog|export_history|write_csv`、`csv|writerow|StringIO|lineterminator|dumps|join\(` 等，范围 repo 根目录）确认：全库只有这两处 CSV 实现，`export_catalog`/`export_history` 的唯一调用方是 `src/tests/test_contracts.py:16`。
- **推荐方案**：删除 `export.py:1-11` 的循环，改为 `from shared.tabular import write_csv` + `return write_csv(rows)`（与 `history.py` 一致）。保留 `export_catalog` 这个业务命名不动。
- **商业功能**：
  - 保留：`README.md:5` 要求的"字段内逗号、引号、换行都被保留"，以及测试固定的那组输入的逐字节输出（两者对 `[['a,b','two"quotes','line\nbreak'],[None,12,'plain']]` 产出完全相同的字符串）。

  - 另有仅异常类型的差异（`rows=[5]` 之类误用：`TypeError` vs `_csv.Error`）。
  - 用户量与频率：**未知**（无用量指标）。无法判断单列空值导出在真实场景中是否发生。
- **净收益与代价**：删除一份独立维护的引号规则；catalog→shared 的依赖边已由 `history.py` 存在，不新增依赖；不新增第三方库。**未实测，不给净减行数**，只标明可删范围为 `export.py:1-11` 的循环体。

- **选择**：A 换成 `write_csv`，并按 S3 修复测试（推荐） / B 保留现状两套实现 / C 暂缓，先跑差异点实测再定

### S2 — 把 `src/search/query.py` 的手写修剪循环换成 `strip()`

- **类型**：实现等价；**依据**：已查证（推演层面完备，未实测）

- **推荐方案**：整个函数体替换为 `return query.strip().lower()`。
- **商业功能**：完全保留 `README.md:6`——只修剪两端、内部空白不动（`strip()` 按定义不触碰内部）、整体小写。无行为减少。用户量与频率：**未知**；补充观察：全库搜索显示 `normalize_query` 的**唯一调用方是测试**，生产侧无调用方（repo 外无法排除）。
- **净收益与代价**：6 行手写迭代 → 1 行标准库惯用法；顺带消除首尾空白极长时的 O(n²) 重复切片（**未做基准测试**，无证据表明现实中构成问题，不作为采纳理由）。无迁移成本，无调用方改动。**未实测，不给净减行数。**
- **数据/资金/安全**：不适用 —— 依据是已核查全部调用方（仅测试一处），该函数当前未接入任何缓存键、去重键或身份比较；特别确认它**没有**参与 `billing/collect.py` 的 `request_key`（后者是完全独立的、不做规范化的大小写敏感字典查找）。若将来接入键派生，`İ` 小写展开为两个码点的多对一问题需重新评估 —— 那是未来条件，不是当前发现。
- **验证方法（本次未执行）**：对上述边界输入比对新旧实现输出；现有 `test_query` 可原样继续作为回归。
- **关联**：无

## 安全发现与未决限制

以下是调查中发现的**既有缺陷**，不是简化收益，本次也**未做任何修复**。协议要求记录而非借机修复。

**数据完整性**

- **D0 — `src/catalog/export.py:10-11`：单列空值行静默丢列。** 单字段且为空或 `None` 的行序列化为裸 `'\r\n'`，被合规 CSV reader 读回是零字段记录，该列在往返中消失。S1 恰好消除这条路径（这也是 S1 的输出"变化"实为纠错的原因）。**往返行为系手工推演，未实测。**

**资金与记录完整性（`src/billing/collect.py`）**

该文件的副作用链只有一种顺序：`request_key in ledger` 检查 → `gateway.charge()`（资金、外部、不可逆）→ `ledger[request_key] = record`（本地记录）。**扣款之前没有任何 pending/意图记录，也不存在"先记账后扣款"的顺序。** 已扣款的副作用不会因为后续抛异常而自动撤销。

| ID | 位置 | 场景 | 用户可见终态 | 代码内恢复途径 |
|---|---|---|---|---|
| **D1** | `collect.py:5-6` | 网关已扣款但响应丢失/抛错；或扣款成功后账本写入抛错 | 已扣款，**无任何记录**，异常向上抛出且不携带"钱已经动了"的任何信号 —— 对账缺口无声 | **无** |
| **D2** | `collect.py:3` vs `README.md:7` | 同一发票用两个不同 request key 提交 | 同一发票**被扣两次**，两条账本记录，无检测。判重键**只有** `request_key`，代码从不比对 `invoice_id`；网关的 per-request 幂等键因两次 key 不同也不会去重 | **无** |
| **D3** | `collect.py:3-6` | 同 key 并发/重入：检查与写入之间隔着整个网络调用（TOCTOU） | 两次调用都进入 `gateway.charge`；第二次账本写入**覆盖**第一次，一笔扣款彻底失去记录。本地判重在并发下**完全不提供保护**，唯一后盾是网关幂等键（仓库内不可验证） | **无** |
| **D4** | `collect.py:5-10` | 网关以返回值（拒付/`None`/事后冲正）而非抛异常表示失败 | 失败扣款被记为成功收款，此后第 3-4 行永久拦截所有重试，该发票无法再通过此路径收款 | **无** |
| **D5** | `collect.py:3-4` | `request_key` 跨发票复用、为空或为 `None` | 返回**另一张发票的收据**，调用方以为收款成功而实际未扣款。无任何键校验 | **无** |

其中 **D1 与 D3 最高**：二者都产生"钱已移动但无持久记录"，正是 `README.md:7` 点名的记录完整性底线。**Billing 分区测试覆盖为零**（已确认非假设：`test_contracts.py:5-7` 只导入 catalog 与 search 三个符号，全库 grep 在任何测试文件中无 billing 命中）。
