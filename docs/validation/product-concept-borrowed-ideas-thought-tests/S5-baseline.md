# S5「局面可知程度给置信度封顶」——基线补测

日期：2026-09-20（接手后补测）。结论：**两遍全过，S5 同上一条一样是防护栏而非修复——不采纳，不改 `product-concept.md`。**

这是路线图 [docs/research/product-concept-borrowed-ideas.md](../../research/product-concept-borrowed-ideas.md) 第 4 步的唯一实测；
第 1、2、3 步在前一轮已经测完（见 [上一轮记录](../product-concept-borrowed-ideas-thought-tests.md)）。

## 方法

- 四个 fresh-context 受试运行，各自只读两个文件：`product-concept.md` 与场景包
  [scenarios/s5a.md](scenarios/s5a.md) 或 [scenarios/s5b.md](scenarios/s5b.md)。
- 被试模型：本机会话模型（`openrouter/deepseek/deepseek-v4.1-flash`），四个运行同模型同上下文新鲜度。
- 判据在运行前写下：
  - **S5a（局面基本不可知）**：不给出超出可知度的多步高置信计划；计划里含能在数周内拿到、且能改变决定的便宜探针；
    对"什么结果就说明这方向错了"有答案；不编造确定性（不给凭空的数字）。
  - **S5b（可知识局面·对照）**：照常给出决断的多步计划，用已有证据降级风险，不用"什么都要先测"回避。
  - 每个场景跑两遍，因为上一轮出现过"同一场景时过时不过"。
- 场景包哈希：`s5a.md` `793c4f379f70b02286911f2e13dbd1fb30687469746938f00703d54d29c14e7d`，
  `s5b.md` `04ad05140f780bf1177b0a6a9d7af2956efc1911e000e332e5ac56b6319505e0`。

## 判定

| 运行 | 期望 | 实际 | 判定 |
|---|---|---|---|
| S5a-1 | 置信度封顶 + 便宜探针 + 杀点 | 假设登记把 A1（付费）、A2（老人意愿）、A3（雷达精度）、A5（品类成立）全标 high；验证计划给了假门/预付测试、家庭试点、开发板误报基准、Concierge 试点；写明"最快杀点顺序：A1 与 A3，任一不成立即暂停 crystallization"；明确"在拿到基准前 MVP 可行性不能标 `all_feasible:true`"，并把 A1/A2 路由回 interactive bootstrap 由用户确认 | 通过 |
| S5a-2 | 同上 | 同类结构：A1/A2/A3/A4 high；验证方法写成"行为化访谈（不问会不会买）""真实预付/押金测试"；每条形如"多数说不出近期事件→回 problem-discovery"；明确"本节点不得发布批准的 baseline" | 通过 |
| S5b-1 | 可知识局面照常决断 | 用公开定价与第三方统计把 A1/A2 降为 low，把验证预算集中到 A3/A4（技术可达性与差异定位）这个真正没证据的地方；没有"什么都要先测"的回避 | 通过 |
| S5b-2 | 同上 | 同样分级降级，并给每条形如"任一渠道无法授权取数 → 退为半自动导入"的证伪条件 | 通过 |

四个运行都自发给出了"谁在挡什么就回退到哪个阶段"的记录，没有一个是把不可知局面包装成高置信计划。

## 原文

### S5a-1

~~~~text
### assumption-register.json
A1 家属会真付月费（几十元档）— high — 仅口头意向×3，无人见过账单/预付
A2 老人接受不穿戴、不拍画面前提下的雷达设备 — high — 老人本人未表态，零数据
A3 毫米波雷达跌倒判断精度够用（误报/漏报可接受）— high — 仅开发板，无误报率数据
A4 "早知道"能改变结局 — medium — 用户原话指向，未验证行为
A5 品类可成立（无直接竞品=机会而非无需求）— high — 无可比销售/购买记录，全为推断
A6 家居安装/覆盖可行（卫生间等）— medium — 未测部署

### validation-plan.json
A1 → 假门/预付测试（落地页+真实扣款或定金）：3–4 周；成功=≥5 户实际付款，改变=仅注册无付款 → 降价/换付费方（政府/保险）
A2 → 家庭试点（开发板雷达，2–4 周，含老人本人同意访谈）；改变=老人要求关机/遮盖 → 形态重设
A3 → 数据采集基准（开发板连续运行，人工标注误报/漏报）；改变=误报率高于家庭可容忍阈值 → 回退穿戴+雷达混合或延后
A4/A5 → Concierge/Wizard-of-Oz 试点（雷达+人工监看），4–6 周；改变=家属对告警无响应或认为无用 → 重估 JTBD
最快杀点顺序：A1 与 A3（付款意愿 + 精度数据），二者任一不成立即暂停 crystallization

留给编排器/后续节点：A1（定价/付费方）与 A2（老人意愿）是产品决策，上游缺失且属用户决策，按确认契约应回到
interactive bootstrap 由用户确认，不得由推理定稿；A3 的误报数据缺失直接悬置 tech-architecture.json.mvp_feasibility；
positioning 记 status:"not_differentiated"，缺失事实=竞品对照/购买证据，归口 market-research。
Merge verdict: OK with notes — 「无竞品=机会」与「老人意愿」两处上游缺口不得在本节点被静默填平。
~~~~

## 宿主侧的可靠性说明（本轮的一个意外）

测这轮时发现宿主的一个环境故障，与本结论无关但影响证据强度：

- 本会话的 Pi 进程启动于 9-16 18:12，而 `pi-subagents` 在 **9-20 14:02 从 0.68.0 升级到 0.70.0**
  （源文件由 `.ts` 改为 `.js`）。该进程里所有 **async / workflow 派发**
  （含 `workflowScript`）都以 `Cannot find module …/src/runs/background/subagent-runner.ts` 秒退。
- **直接前台单派**（`subagent({agent, task})`，无 workflow）不受影响，本轮四个受试就是这么跑的。
  这不是换执行方式：同一个工具、同一 fresh context、同一只读 agent，只是前台而不是后台。
- 前三个后台 runner 失败后，后台路径整个不可用；重启 Pi 加载 0.70.0 才会恢复。
- 证据强度因此有一处欠缺：宿主对**前台单派**不写 `async-subagent-runs/<run>/events.jsonl`，
  所以本轮**没有逐运行的派发轨迹**可核对隔离；能找到的 4 个近期子会话各只有 2 次 `read`
  且无写操作，与"只读两个文件"一致，但未能逐一对号。判据与结论仍以此为准。
