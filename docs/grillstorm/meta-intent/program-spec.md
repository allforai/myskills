## Interface semantics

I-scope: bootstrap-profile captures explicit task goal, route (local-change|product-reconstruction|new-product), relevant scope and requirement references. Local requirements carry goal/rules/acceptance plus provenance of user confirmation; unresolved fields block dependent work. Route cannot be selected from file presence alone. Output includes independently chosen implementation/documentation/verification responsibilities, not just a classifier.

I-intent: extend existing product-concept + decision-journal responsibility; retain old batches and add stable item/decision identities, revision, provenance, uncertainty, disposition, confirmation and lineage. Draft facts/inferences/unknowns are not confirmed decisions. Four explicit operations confirm/add/adjust/remove; add need not cite code. Preserve history and discussion never edits product source. Confirmed scope includes explicit exclusions; pending items never enter authority by silence. Consumers reference the approved item/revision they depend on. Baseline publication and journal decision must remain consistent on interruption: validate inputs first, stage update and publish authority last; incomplete projections are detected/blocked on reentry, not used as confirmed evidence. Reapplying a recorded decision is idempotent.

I-resume: observable bootstrap/resume boundary accepts existing artifacts + new scripted user decisions and returns outstanding questions and relevant eligibility. Legacy records lacking provenance remain unverified only where needed; do not erase them or replay full interviews. Readiness distinguishes globally unsafe environment/configuration failures from node-scoped pending product prerequisites. Pending decision closure propagates through hard dependencies, preserves independent completed/evaluable branches, never asks during run, and final overall status remains blocked while required work is pending. Return to interactive bootstrap resolves decisions and recomputes eligibility. Do not redesign human approval/dashboard machinery.

I-freshness: bind required docs, execution contracts and accepted evidence to content-based relevant source snapshot, confirmed baseline revision/content and input dependencies. Compute current fingerprints from actual files, not trust report claims or mtime. Distinguish deletions and different dirty states on same commit. Explicit input/dependency declarations separate product inputs from generated outputs, logs and control-plane reports to avoid self-invalidation; downstream dependencies still invalidate when their true producer inputs change. Missing/unreadable/unknown inputs yield explicit uncertain/invalid evidence, never fresh. Compute direct changes then hard-dependency closure; unaffected evidence retains its original proof. Existing audit index is not itself completion authority. Repeated unchanged inspection has stable semantic state, ignoring diagnostic timestamps.

I-sync: planning names required fact documents, decision references, execution contracts, verification and repair owners. Completion gate compares current fingerprints and required documentation/evidence, including meaningful non-empty report checks, accepted statuses and declared requirements; a matching hash is freshness, not proof of semantic truth. Actual inspection/verification is mandatory before stamping accepted evidence. Stale/missing/conflicting input emits typed blockers with responsible node and current differences; repair and sync precede rerun. Approved product changes are applied only from journal-backed decisions; unknown decisions return to interactive prerequisite state. Recovery reuses same gate; code-test success alone cannot close stale docs.

I-drift: bootstrap/resume compares current inputs with last accepted state. Agent verifies semantic effect; recorded implementation-only observations permit fact refresh, while behavior change or uncertain semantic effect stays a conflict. No deterministic hash check is allowed to infer product approval. Explicit accept records a user decision and new baseline then reuses I-sync; reject preserves baseline and creates scoped repair then I-sync; defer/interruption preserves conflict and blocks its dependency closure. No alternate external-drift acceptance system. Repeated resolution is idempotent and historical decisions remain auditable.

## State / failure / compatibility

Verification identity boundary (SG-01): every observation records the exact source/baseline/dependency manifest it consumed. Verify immutable captured inputs or establish their stability through publication; never compute only a later manifest and attach an earlier result to it. Completion compares the observed manifest to current relevant inputs. A-to-B change between observation and publication rejects A proof for B, retains historical evidence and unaffected branches, and requires affected reconciliation/sync plus actual B re-verification before acceptance. Exercise this interleaving through the public completion/reconciliation seam, then prove unchanged B rerun stable. This is input identity, not a background watcher or global source lock.

Success requires current confirmed scope and real outputs/proof. Empty route/decision or absent answer stays pending, empty acceptance is invalid. No implicit degraded product behavior is authorized. Validate malformed/ambiguous contracts visibly before writes; preserve prior approved state and exact diagnostic rather than default empty/fresh. Interruption and replay preserve decision IDs/history; pending publication is non-authoritative until consistent. Per-project single logical writer for baseline/snapshot publication; parallel downstream nodes read frozen inputs. Reject conflicting revisions; retry the same contract or reenter bootstrap. No global rollback of unrelated product files. Legacy artifacts remain readable, but unproven approval/freshness cannot be upgraded automatically. Required errors carry node/scope and repair ownership when possible, global errors remain fail-closed.

## Proof and authority

Candidate loading boundary (SG-02): each subject explicitly loads the run-owned candidate bootstrap Skill/host adapter and canonical helpers by resolved path from an immutable or verified-stable candidate checkout/snapshot; no installed-skill update. Record hashes/revision of actual loaded candidate dependencies separately from provider/model version and non-secret dispatch identity. Check loaded paths/tool traces match the requested candidate; installed/candidate mismatch is unverified, never credited. Evaluate a deliberate mismatch and relevant adapter change: changed loaded candidate inputs invalidate affected prior scenarios on both hosts, requiring fresh-context retest before final integration. Preserve unaffected applicable proofs. Evidence-index/fixture responsibilities own this check; no new independent harness or cleanup API. Failure-ledger proof requirements are exercised through existing public seams and declared scenarios/controlled fault injection, not a new production feature for each failure mode.

Approved high-level seam is bootstrap/resume inputs and outputs, using repository fixtures and scripted user decisions. Shared helper tests plus actual Claude/Codex scenario runs are complementary. Each implementation ticket must include behavior tests through public CLI/validation boundaries and both adapter integration. Thought-test agents receive minimal raw scenario, current Skill and user responses, never the issue acceptance text or evaluator oracle. Evaluators retain independent expected outcomes. Failure must link exact artifacts, owning ticket and minimal reproduction, then fresh-context retest after repair. Unavailable host means unverified, not a substituted pass. Root performs final fixed-ref full suite and independent Standards/Spec review after task proofs.

Authorized: local repository skill implementation, isolated fixtures, scripts/tests, run-owned task commits after review. No target-product source mutation during discussion; no push/deploy/install updates or production/external paid side effects. No background watcher. Original checked-out worktree remains untouched by this run; integration publication serialized. Main branch is externally active; recheck before eventual merge and defer if user changes would be absorbed/overwritten.
