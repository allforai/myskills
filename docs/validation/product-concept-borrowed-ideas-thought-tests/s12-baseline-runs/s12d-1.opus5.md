# S12d — user-role-definition 产出（家教撮合平台）

## 角色与 JTBD + VPC
1. **R1 家长（消费方）** job：*当孩子某科跟不上、自己没能力辅导时*，把孩子交给一个能信的人，并确认每次来上课的就是当初见过的那个人；在还没摸清对方之前不把一整期的钱押出去。（去掉这个平台，这两句仍成立。）Pains：试课与上课换人、一次付一学期没底、抽成不透明、换人没人管。Gains：来人可核对、钱跟着已上的课走、不满意能换。Relievers/Creators（**解法候选，非已批功能**）：身份与学籍可核验且与到场人一致、按课时计费与未上课时可退、投诉有结论。
2. **R2 大学生家教（生产方）** job：*当课余有时间、想靠自己学的东西挣钱却没渠道时*，让附近有需要的家庭主动找上我，且课上完钱按时到手。Pains：无渠道被看见、抽成、月结拖、被临时取消白跑。Gains：有稳定询单、上课量被认、按时结算。Relievers/Creators（候选）：按地理/科目被看见、打卡即计量、结算周期缩短。
3. **R3 平台一线（审核＋客服，运营方）** job：*当每天 400 单新信息和 100+ 件纠纷涌进来、而我不认识任何一方时*，凭手上材料给每一件一个站得住的结论，且同一件事不回头找我第二遍。Pains：量大、材料真假难辨、结论要能追溯。Gains：待办有序、判断有依据、处理留痕。
4. **R4 平台管理（政策与风控，运营方）** job：*当某城市或某个家教持续出问题时*，改规则本身（服务费比例、是否暂停接单）并对后果负责。与 R3 拆开的理由：一线不应拥有改费率/停号的权限，后果量级不同——这是角色边界，不是页面划分。

## Producer-side closure check
- 消费↔生产闭合：R1 消费的课时全部由 R2 生产，平台不生产教学内容。
- 运营侧：上游列的 7 项日常事务（家教资质审核／订单审核／投诉／课时费结算／退款／差评处置／费率调整）**全部**落在 R3/R4，而上游明确没说平台方有多少人、现在怎么处理。此处没有能由证据支撑的选项，按能力文件记为**开放问题（来源：用户）**，不默认"自动审核就够"或"一个后台就够"。
- 未闭环①资金：按打卡结算＋家长退款意味着钱要停在某处、并有人对账与出款。钱是平台代收还是直付家教，上游未定——这是产品选择而非实现细节，路由回 business-model ＋ 交互确认，本节点不替用户定。
- 未闭环②课时确认：打卡目前是生产方自证自己的工作量，家长侧确认是否存在未知；谁的确认算数，直接决定 R1「钱跟着已上的课走」和 R2「上课量被认」两个 job 能否成立 → 开放问题。
- 未闭环③获客：竞品里现成路径是"家长群互相推荐"，但上游没说平台靠什么被家长找到；这决定客户端集合（见下），未定不补。

## 多客户端声明
| role | clients | feature_parity |
|---|---|---|
| R1 家长 | `parent-ios`(swiftui-ios/ios)、`parent-android`(kotlin-android/android) | `full` |
| R2 家教 | `tutor-ios`(swiftui-ios/ios)、`tutor-android`(kotlin-android/android) | `full` |
| R3 一线 | `ops-console`(react-spa/desktop-web) | 单客户端（legacy `app`+`client_type` 等价） |
| R4 管理 | 同 `ops-console`，仅权限不同（**推荐默认，待确认**） | 单客户端 |

- R1/R2 未列 web/H5：上游没有任何证据说明家长或家教从桌面端进来。若获客确定走微信/网页分享，R1 需补 H5 客户端并转 `partial`（`parity_exceptions` 至少含"推送提醒仅移动端"）。待用户确认，不擅自添加客户端。
- R4 是否独立控制台：权限不同不等于客户端不同；推荐同一控制台分权限，但这决定要不要多一个前端工程，需用户点头。

## 留给编排器／后续节点
- 开放问题（必须回交互确认，后续节点不得自行假设）：平台方人力与现有处理方式；资金归属（代收／直付）；课时确认由谁说了算；C 端获客渠道→客户端集合；R4 控制台是否独立。
- 可直接下传的量：R3 日均 400 单审核 + 100+ 件投诉/退款工单；写入 `concept-baseline.roles[].high_frequency_tasks` 时按此量级，不要把运营侧写成低频后台。
- 本节点 VPC 里的 relievers/creators 一律是解法候选：feature-gap / ui-design 的范围只能是用户在计划确认里点头过的那批任务，不得把这里的候选当已批范围；本节点不产出 positioning / ERRC 判断；tech-architecture 需知审核与工单是量级驱动的内部后台，不是轻量 CRUD。
