# S12c role-profiles / vpc-per-role（`user-role-definition`，无人值守产出）

**角色与 JTBD + VPC**（job 一律写处境「当…」，不含任何功能/界面名；把本产品从世界里拿掉句子仍成立）

| 角色 | Job（when…） | Pains | Gains | Pain Relievers / Gain Creators |
|---|---|---|---|---|
| R1 素材采购者（做设计/做自媒体，月付） | 当手上稿子已排期、要配图配乐时：赶上交付，且日后没人能找上门说这张不能用 | 找一张合适的要翻半天；用完担心被追责；单张零售价撑不住出稿频率 | 敢把成品交客户；成本可预算 | 每次取用留一份可出示的授权凭据（范围/期限/主体）；按用途而非关键词收敛候选；固定月费覆盖不限次取用 |
| R2 创作者（摄影师/插画师/音乐人） | 当手里拍完画完做完的作品闲置、又不想逐个谈授权时：让它们持续带来收入，不必自己应付买家和合约 | 逐笔议价耗时；不愿买断失去作品；分成算不清 | 被动收入；作品仍归自己 | 代授权不买断；按下载量的可核对账单 + 按期打款 |
| R3 内容准入与风险审核（平台侧） | 当大批他人的作品要经我手转给别人使用时：不让有权利瑕疵的流出去，又不把人等跑 | 版权/肖像/敏感三类风险靠肉眼；被投诉时说不清当初凭什么放行 | 误放行率低；处置有据 | 入驻与单件素材的留痕判定；投诉→下架的可追溯链路；同类素材批量排查 |
| R4 结算与退款（平台侧） | 当一个结算周期结束时：每个人该拿的钱准确按时到账，事后对得上账 | 下载量→金额口径争议；退款/下架后的追回 | 争议少、可对账 | 周期账单与打款记录同源；退款与下架对分成的影响记在同一条账上 |
| R5 权利方/投诉人（外部发起） | 当我发现自己的作品被人拿去卖或用时：尽快让它停下来，并知道谁用过 | 找不到受理入口；不知处理进度 | 停止传播、拿到使用记录 | 受理入口 + 处理状态回执（入口形态未定，见 O3） |

**Producer-side closure check（谁生产、谁运营）**
- R1 消费的东西由 R2 生产；R2 能被取用靠 R3 放行、能拿钱靠 R4；R1 的"来源清楚"本身就是 R3+R4 的留痕产物——消费/生产/运营三侧闭合。
- 上游列的 6 项平台事务已全部归到 R3/R4（审核入驻、审核上传、投诉下架 → R3；分成打款、订阅退款 → R4；批量排查 → R3 主办、影响 R4 追回）；但两者**权限性质不同**（内容判定 vs 动钱），不默认同一人；平台方人手与现状上游未给，1 人兼两职还是两个角色属产品级选择，本节点不定（O1）。
- 缺口：R5 是唯一没有客户端的参与方 → 侵权投诉这条流程在产品里目前**没有起点**（O3）。

- **O2 证据缺口**：本节点未做 WebSearch（无人值守未授权），能力要求的"典型用户构成/真实用户反馈"无证据 → 买家规模比例、"做设计"与"做自媒体"是否该拆成两个角色（付费意愿与选图方式可能不同）、买家是否需要移动端，一律标**未查**，不填数字、不合并。
- **O3 开口问题（无证据可据以推荐）**：投诉受理入口形态——公开表单免注册 vs 邮件转人工 vs 仅限已验证权利方——交用户选。
